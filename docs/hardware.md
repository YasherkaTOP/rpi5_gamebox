| Ввод звука | `plughw:CARD=Device,DEV=0` (C-Media, родные частоты только 48000/44100 — 16 кГц через ресемплинг) |

| Пользователь сервисов | `gamebox` (uid 999, gid 984), группы audio, video, input, render |

## Плата и загрузка

- Raspberry Pi 5 Model B Rev 1.1, 8 ГБ (ревизия `d04171`), Active Cooler.
- EEPROM: 2026-10-30 (`42d1b6a9`), канал `default`, актуален. `BOOT_ORDER=0xf14` (USB → SD → повтор).
- Загрузочный носитель сейчас — **microSD 233 ГБ** (`mmcblk0`), а не USB SSD: SSD вышел из строя, замена — за владельцем.
  Благодаря `BOOT_ORDER=0xf14` загрузочный USB SSD будет выбран автоматически, как только появится.
- ФС: ext4 с журналом (`has_journal`), опции корня `rw,noatime` (уже в образе).

## ОС

- Raspberry Pi OS 64-bit, сборка `reference 2026-10-06`, Debian 13.7 (Trixie). **Образ с рабочим столом**
  (`pi-gen stage4`, `lightdm`, цель по умолчанию `graphical.target`) — расходится с §4, см. открытые пункты.
- Ядро `6.18.60+rpt-rpi-2712`, Python 3.13.5.
- Своп: только zram, `/dev/zram0` 2 ГБ, zstd (штатный `rpi-swap`, настроек не меняли). Файл `/var/swap` существует, но не подключён.
- Время: `Europe/Moscow`, `systemd-timesyncd`, синхронизировано по NTP.

## Питание

- Штатный блок 27 Вт распознан: `max_current=5000`, `usb_max_current_enable=1` (лимит USB 1,6 А).
- `EXT5V`: 5,15 В в покое; под нагрузкой минимум 5,126 В, медиана 5,150 В.
- `get_throttled=0x0` всё время; предупреждений о питании и over-current в `dmesg` нет.
- **Экран питается от USB Pi** (решение владельца по итогам прогона ниже).

Условия: открытый корпус, комната ~26 °C, экран: яркость 60, громкость 60 (кнопки экрана).

устройстве, а hailo-ollama отвечал на это HTTP 200 с ошибкой в теле (89 577 «успешных» запросов по 0,5 мс). Скрипт
исправлен: проверяет модель до старта и считает ответы с `"error"` неудачными. Часовой прогон не делался.

## Hailo-10H

| Что | Значение |
| --- | --- |
| Устройство | Hailo-10H `1e60:45c4`, PCIe Gen3 x1 (8 GT/s; x4 у чипа → x1 у Pi — норма) |
| Прошивка | 5.1.1 (release, app), архитектура `HAILO10H` |
| HailoRT | 5.1.1 (`h10-hailort`, `python3-h10-hailort 5.1.1-1`) |
| Драйвер | `hailo1x_pci` 5.1.1 (DKMS), загрузка прошивки при старте ~3,7 с, `/dev/hailo0` готов на 7,7 с после старта ядра |
| GenAI Model Zoo | `hailo-gen-ai-model-zoo` 5.1.1, сервер `hailo-ollama`, порт 8000 |

**Хранилище hailo-ollama** (выяснено через `strace`):

- манифесты: `/usr/share/hailo-ollama/models/manifests/<имя>/<тег>/manifest.json`, поле `hef_h10h` — SHA-256 файла;
- файлы моделей: `/usr/share/hailo-ollama/models/blob/sha256_<sha256>`;
- конфиг: `~/.config/hailo-ollama/hailo-ollama.json`, иначе `/etc/xdg/hailo-ollama/hailo-ollama.json`
  (библиотека моделей — `dev-public.hailo.ai:443`). Пустая папка `~/.config/hailo-ollama` роняет сервер (`parse_error`);
- сервер падает целиком (`bad hash`), если скачанный файл не совпал по хэшу.

`/api/pull` из России без VPN не работает. Модель ставится вручную: `.hef` скачивается на ПК и раскладывается скриптом
`deploy/hwcheck/hailo_install_hef.sh`.

**Установленная модель:** `qwen2-instruct:1.5b` — файл `Qwen2-1.5B-Instruct.hef` с сайта Hailo Model Zoo,
1 657 568 559 байт, sha256 `e84348ba1ecbcb3b5f60defca8e15166241ae1e96ff2db832b8b5998c1f0039d`. Манифест сделан из
`qwen2:1.5b` (шаблон чата Qwen2 с системным промптом «You are a helpful assistant.»).

**Эталонная генерация** (`60_hailo_smoke.sh`, потоковый `/api/chat`, 3 запроса, грубо):

- первый запрос: 9,3 с до первого фрагмента (загрузка модели в Hailo);
- дальше: 0,34 с до первого фрагмента, ~6–8 токенов/с;
- качество на глаз слабое: «2 + 3?» → «Четыре», «какого цвета небо днём?» → «Белое». Выбор модели — блок 3.

## Экран и сенсор

- EDID: производитель `MPI`, модель `MPI7002`, родной режим 1024×600 @ 60,04 Гц (первый detailed timing),
  basic audio. Подключён ко второму micro-HDMI (`HDMI-A-2`). Консоль на весь экран, резко, без полей.
- Сенсор QDtech MPI7003, USB `0484:5750`, `usb-xhci-hcd.1-2`. Касания углов (raw): ЛВ (11, 35), ПВ (1017, 21),
  ПН (1006, 595), ЛН (11, 587) — оси совпадают с картинкой, поворот и зеркало не нужны.
- Громкость и яркость регулируются только кнопками экрана; рабочие значения — 60 и 60.

## Звук

**Вывод (HDMI).** ALSA-карты: `vc4hdmi0` (card 0, не используется), `vc4hdmi1` (card 1, экран). Устройство
`hdmi:CARD=vc4hdmi1,DEV=0`; `plughw:` для HDMI на Pi 5 не работает. Регулятора громкости в ALSA нет.
Шумов и треска в тишине нет.

**Ввод (кодек).** C-Media «USB PnP Sound Device», USB `08bb:2902`, card 2, id `Device`, full speed (12M).
Захват: S16_LE, 1 канал, **только 48000 и 44100 Гц** — 16 кГц получается ресемплингом (`plughw`), в блоке 5
лучше захватывать 48 кГц и ресемплировать самим. Микшер: `Mic Capture Volume` 16 из 16 (максимум, +23,8 дБ),
`Auto Gain Control` — есть, **выключен**, `Mic Playback Switch` (прослушка) выключен.

**Микрофон.** Петличный, на лицевой стороне, направлен на игрока, в мягкой втулке, ветрозащита надета,
5 см до динамика экрана; вентилятор сзади экрана.

**Запись речи с 0,5 м** (`30_mic_check.py`, вентилятор принудительно на максимуме, 8–9 тыс. об/мин):

| Запись | Пик, dBFS | Уровень кадров 30 мс, p95, dBFS | Клиппинг |
| --- | --- | --- | --- |
| Шум (10 с) | −21,8 | −37,2 (медиана −37,8) | 0 |
| Речь, обычный голос (15 с) | −17,7 | −36,3 | 0 |
| Громко (6 с) | −18,1 | −33,9 | 0 |

Речь выше шума на **1,5 дБ** — критерий «заметно выше шума» не выполнен. Уровень по 0,25-с кадрам почти не
меняется (−38…−33 dBFS), то есть речь почти не отличима от фона, хотя усиление на максимуме. Щелчки из динамика
в 5 см тот же микрофон ловит с запасом 47 дБ (узкополосно), так что тракт живой, а слабое место — чувствительность
петлички к голосу с 0,5 м или собственный шум кодека. Владелец принял как есть до калибровки; см. открытые пункты.

**HDMI после тишины** (`40_hdmi_audio.py`, серия из 20 щелчков 3 кГц через 50 мс, громкость 60):

- обрезания нет: после 5, 30 и 60 с тишины (по 2 раза) первый щелчок стоит в записи там же, где в «тёплом»
  эталоне (расхождение < 2 мс), разрешение метода 50 мс;
- дополнительной задержки старта после тишины нет (в пределах нескольких мс);
- на слух владелец иногда замечает лёгкое «проглатывание» — проверить в блоке 5;
- **абсолютная задержка не измерена:** метод привязывал момент записи к часам неверно (выдал 5–6 мс, что физически
  невозможно). Точная калибровка — блок 5.

## Сеть и доступ

- Wi-Fi `wlan0`, 2,4 ГГц (канал 1), сигнал −59 dBm; Ethernet не подключён.
- mDNS: `ssh admin@gamebox.local` с ПК работает.
- SSH: **вход по паролю включён** вместе с ключом (решение владельца: домашняя сеть). `PermitRootLogin without-password`.

## Время загрузки ОС

- `systemd-analyze`: 2,097 с ядро + 13,438 с userspace = **15,5 с**; `graphical.target` — 7,5 с в userspace.
- Секундомер: ~15 с от подачи питания до приглашения на экране.
- Крупнейшие: `NetworkManager-wait-online` 5,97 с, `apt-daily-upgrade` 3,19 с, `systemd-binfmt` 2,32 с,
  `NetworkManager` 1,33 с, `fsck` загрузочного раздела 1,28 с. Это база для 60 с до главного экрана (блоки 12, 21).

## RTC

- Батарейка CR2032 в J5, зарядка выключена (`rtc_bbat_vchg` не задан) — правильно для неперезаряжаемой батарейки.
- В отчёте 2026-11-23 RTC не хранил время без питания: ядро взяло из RTC `1970-01-01T00:00:39`,
  `battery_voltage` = 0, `BATT_V` = 0,000 В.
- **23.11.2026 владелец исправил батарейку и проверил: время сохраняется.** В сыром отчёте этого ещё нет;
  при следующем `00_collect.sh` в `collect/time.txt` должно быть текущее время в строке `rpi-rtc … setting system clock`
  и ненулевое `battery_voltage`.
- `hwclock` в образе нет (пакет `util-linux-extra`).
